# Proof — TestRail CSV export (issue #35), generated from US-004

`US-004-testrail-import.csv` is a real export produced by applying the mapping rules in
`plugins/qaia-core/skills/generate/connectors/testrail.md` to the actual US-004 test book
(`examples/expense-demo/qaia-journey/testbooks/US-004/*.feature` + `coverage-matrix.md`). Nothing in
this file is hand-written or fabricated — it was generated by parsing the real `.feature` files. This
is the same US-004 test book already used to validate the Xray export (`../xray/`), reused here for a
direct, apples-to-apples cross-check between the two connectors.

## How it was built and checked

A one-off Python script (decision D42 — session-generated, jettable, not shipped code) parsed the 4
`.feature` files, applied `connectors/testrail.md`'s mapping table — `Given`→`Preconditions` (Background
flattened in, same spirit as the Xray connector's Background handling but landing in TestRail's own
dedicated field instead of being force-merged into one text blob), `When`→`Steps`, `Then`→`Expected
Result`, `#` comments relocated into `References` (TestRail's Text template has no documented
freeform "Description" field the way Jira/Xray does, so the rationale/confidence text goes there
instead of being invented a new column) — wrote the CSV with Python's `csv` module
(`csv.QUOTE_ALL`, RFC 4180 quoting), then **re-parsed its own output** and asserted:

- header row matches the 8 documented columns exactly (`Title`, `Type`, `Priority`, `Preconditions`,
  `Steps`, `Expected Result`, `Section`, `References`);
- 38 rows (matches `synthesis.md` and the Xray export's own row count exactly — 1 smoke journey + 37
  condition scenarios);
- 38 distinct `QAIA-US-004-nnn` IDs (embedded in `References`), no duplicates, no scenario missing one;
- no `Preconditions`/`Steps`/`Expected Result` field contains a leaked `#` — every QAIA comment was
  relocated to `References`, not dropped or left in place;
- `Type` is `Automated` and `Priority` is one of `Critical`/`Medium`/`Low` on every row;
- the `Priority` distribution came out **19 Critical / 15 Medium / 4 Low** — the same 19/15/4 split as
  the Xray export's Highest/Medium/Low (P1→Critical here vs. P1→Highest there — different target
  scales, same source distribution), an independent cross-check that this export didn't silently drop
  or reprioritize any scenario either;
- the file round-trips as valid UTF-8 at the byte level, not just via a terminal that may mis-render
  non-ASCII characters like the € signs and em dashes in the scenario text;
- **2 of the 38 rows have a genuinely empty `Steps` field** — pure state-check scenarios with no
  `When` at all (`A report just under €500 needs only the manager's approval` and `A manager's own
  small report escalates directly to finance`, both `Given…Then` with nothing done in between). This
  is called out explicitly in `connectors/testrail.md` as an honest reflection of the scenario having
  no action, not a mapping defect that got silently swept under the rug.

No `Scenario Outline` appears in US-004, so the `-eN` explosion rule (documented in
`connectors/testrail.md` for consistency with the Xray connector and the XLSX deliverable) is
specified but not exercised by this proof.

## What this does and does not prove

**Proves**: the connector's mapping rules — including the Given/When/Then split, which is new to this
connector and not something the Xray connector needed — are mechanically applicable to a real,
previously-generated QAIA test book, and the resulting CSV is syntactically well-formed per the
documented schema.

**Does not prove**: that TestRail actually accepts this file through its own CSV/Excel import wizard.
No live TestRail instance was available in this session — see the honesty section of
`connectors/testrail.md` for the exact caveats (the `Type`/`Priority` values are QAIA defaults that
still need reconciling in the wizard's step-3 value mapping, TestRail's docs don't use the term "RFC
4180" even though this connector writes to that spec, and a native "Behaviour Driven Development"
template exists in current TestRail that was noticed but not investigated as a possibly better fit).
Treat this as "well-formed per our own reading of TestRail's docs," not "verified against TestRail
itself."
